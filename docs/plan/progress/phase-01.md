## Predict (written before building)

Question: deleting a user cascades to documents and conversations. What happens to a
conversation that cited a document that was deleted first?

Provenance: **[me]** is my own wording; **[Claude]** is what Claude corrected or added.

**[me]** When the document is deleted the conversation must stay with its messages. The
chunks are not deleted, and when the user searches from the conversation the right data
should still appear because the chunks exist. The file's information is stored and saved and
is not tied to the file's deletion.

**[Claude]** Correction: the chunks ARE deleted with the document (cascade; the PRD requires
it), so a search no longer finds anything from that document. What survives is the citation
metadata stored as JSON in `Message.sources` (`documentId`, `documentName`, `chunkIndex`,
`pageNumber`, `sheetName`). There is no foreign key from `Message` to `Document`, so the
conversation and its messages stay, the stored `documentId` dangles by design, and the UI
shows the stored file name. The text itself is gone, and the document cannot be opened.

## Failure drill

What I broke: dropped the foreign key `DocumentChunk_documentId_fkey` in `smartdocs_test`
(not in the dev database), then ran the cascade spec.
What I expected: deleting a document leaves its chunks behind (orphans), so the cascade
tests fail.
What actually happened: 3 of 4 tests failed (`Expected: 0, Received: 3`, `Expected: 2,
Received: 5`, `Expected: 0, Received: 2`); only the conversation/message test, which does not
use that key, passed. Re-adding the key then FAILED: `insert or update on table
"DocumentChunk" violates foreign key constraint ... Key (documentId)=(...) is not present in
table "Document"`. Two orphan chunks existed. I had to empty the test database before the key
could be restored; after that the key was back with `ON DELETE CASCADE` and 8/8 tests passed.
(My first two attempts did nothing because PowerShell mangled the quotes around the SQL; the
passing run then proved nothing. I only noticed because the "FK exists now? expect 0" check
was missing.)
Why:
Provenance: **[me]** is my own wording; **[Claude]** is what Claude corrected or added.

**[me]** Without the foreign key a `DocumentChunk` becomes unknown and rests on no `Document`.

**[Claude]** That describes the orphan correctly but not the "why". The database must enforce
it because code can have bugs and is not the only way in: scripts, manual SQL, future code
and concurrent requests all bypass application checks, while a constraint cannot be bypassed.
The key could not simply be added back because adding a foreign key makes PostgreSQL validate
every existing row, and the two orphan chunks pointed at documents that no longer existed, so
the key was rejected until the data was cleaned. Damage done while a constraint is missing is
not repaired by restoring the constraint.

## Explain back

1. Why is `(documentId, chunkIndex)` unique, and what bug does the constraint catch?
   **[me]** It is unique because `documentId` belongs to one file, and within that file the
   content was turned into text and split into chunks by `chunkIndex`. The error is when the
   same file is searched with the same `chunkIndex`.

   **[Claude]** The idea is right; "searched" should be "written". The constraint stops two
   chunks from occupying the same position in the same document, which is what happens when an
   ingestion step runs twice or retries and writes chunk 0 again: retrieval would then return
   duplicate text and the order would be ambiguous. The key is the pair, not the index alone
   (chunk 0 is allowed in every document, tested in task 1.6), and a batch with one duplicate
   writes nothing.

2. Why `findFirst({ where: { id, uploadedBy } })` instead of `findUnique` plus an `if`?

   **[me]** `findFirst` takes the first result for a given id with a given `uploadedBy`, while
   `findUnique` takes any unique value and excludes similar ones, and the `if` after
   `findFirst` handles the condition fully.

   **[Claude]** This misses the point. The difference is where the ownership check happens.
   With `findUnique` plus an `if`, the query fetches the row by id regardless of owner and the
   code checks ownership afterwards, so another user's row is loaded and the check can be
   forgotten, skipped on one code path, or answer differently from "not found". With
   `findFirst({ where: { id, uploadedBy } })` the owner is part of the query itself: another
   user's id returns nothing, exactly like an id that does not exist, so both become the same
   404 and the existence of the resource is never confirmed (ADR-013).

3. Which index does `WHERE "uploadedBy" = $1 ORDER BY "createdAt" DESC` use, and why?

   **[me]** It uses indexing because it finds the user's rows sorted ascending by creation
   date.

   **[Claude]** Two corrections. It is descending (newest first), and the question asks which
   index: `Document_uploadedBy_createdAt_idx`, the composite on `(uploadedBy, createdAt)`. The
   plan in task 1.7 shows `Index Scan Backward` on it with no `Sort` node: the index is
   already ordered by `createdAt` within each `uploadedBy`, so it is read from the end, stops
   after 20 rows, and touched 23 pages instead of 345.

## Where I was wrong

- The docs assume classic Prisma. npm's `latest` tag was `8.0.0-rc.29` (a release candidate),
  so I pinned the stable 7.10.1 instead. Prisma 7 needs a driver adapter (`@prisma/adapter-pg`
  plus `pg`), a `prisma.config.ts`, and does not read `.env` itself. The generated client is
  written into `src/generated/prisma`, not `node_modules`. Docs that say "`npx prisma ...`"
  still hold; docs that imply `new PrismaClient()` with no arguments do not.
- Installing was slow and failed three times with `ECONNRESET` (slow link to the npm
  registry). A fourth failure was my own: `--prefer-offline` served a stale package list and
  produced `ETARGET` for `scheduler@^0.28.0`, which does exist. Fixed with `--prefer-online`.
- The datasource `url` no longer lives in `schema.prisma` in Prisma 7; it is in
  `prisma.config.ts`.
- The generated client imports its own files as `./x.js`; `tsc` maps that to `x.ts` but Jest
  does not ("Cannot find module './internal/class.js'"). Fixed in the generator with
  `importFileExtension = ""` (bare imports, valid in CommonJS).
- `prisma.config.ts` sits in `apps/api/`, outside `src/`. Once it was type-checked together
  with `src`, `nest build` moved its output to `dist/src/main.js` and silently broke
  `node dist/main`. Fixed by excluding it in `tsconfig.build.json`. I only noticed because I
  booted the built app; the unit tests and the build itself were green.
- `prisma migrate dev` no longer runs `generate` in Prisma 7, so I ran it by hand. A fresh
  clone must run `prisma generate` after `npm install` (the client is gitignored). Add a
  `db:generate`/`db:migrate` script and update `ops/local-setup.md` and `ops/commands.md`.
